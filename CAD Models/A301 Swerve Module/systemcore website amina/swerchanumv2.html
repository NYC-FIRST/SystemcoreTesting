● NYC FIRST · Engineering Documentation

Build, test, and understand the next control system.

Swechanum is a teaching and engineering testbed built around Systemcore, Motioncore, FIRST A301 actuators, and a dual-drivetrain chassis. This guide documents the hardware, software, design process, testing methodology, swerve programming, and vision workflow used to turn the prototype into a repeatable platform.

02 · System architecture

Understand the stack before writing the drivetrain.

The most useful mental model is a layered system: the controller runs the robot software, Motioncore distributes power and communications, actuators provide motion and feedback, and higher-level software turns measurements into robot behavior.

Driver / ControlsGamepad commands, operator intent
→
WPILib Robot CodeSubsystems, commands, kinematics
→
SystemcoreCompute, I/O, CAN interfaces
→
MotioncorePower + device connections
→
A301 / SensorsActuation + feedback
Layer 01

Compute

Systemcore is the robot controller. WPILib describes it as a reconfigurable controller with CAN, I2C, USB, Ethernet, Smart I/O, LEDs, display, and an onboard IMU.

Layer 02

Power + CAN

Motioncore is the distribution layer. FIRST describes 20 individual device ports for point-to-point CAN + power connections, plus three quadrature encoder ports.

Layer 03

Actuation

The A301 combines brushless motor behavior with feedback and closed-loop positioning capabilities, creating one programmable actuator for mechanisms and drivetrain modules.

03 · Quick start

Bring up one device before bringing up the robot.

The safest workflow is incremental. Prove power, communications, firmware, library compatibility, and a single actuator before introducing kinematics or vision.

1

Record your software baseline

Write down the Systemcore image, WPILib version, REVLib version, A301 firmware, Driver Station version, and any vendor libraries. Alpha/Beta systems change quickly; a reproducible baseline prevents “works on my machine” debugging.

2

Build the electrical path

Connect the battery and Motioncore, then connect the Motioncore bridge to Systemcore. Connect only the A301 you are actively testing first. Keep the mechanical load removed during initial software validation.

3

Verify controller access

Confirm Systemcore boots, networking works, and the Driver Station can communicate with the robot. Use the current WPILib/Systemcore instructions rather than relying on legacy roboRIO/Control Hub assumptions.

4

Verify the A301 independently

Deploy the smallest possible motor test. Confirm throttle first, then encoder telemetry, then velocity/position control. Do not debug eight motors at once.

5

Promote the test into a subsystem

Once one motor is predictable, wrap it in a subsystem with clear constants, telemetry, fault handling, and a stop behavior. Only then duplicate the pattern for the other modules.

04 · Hardware

Systemcore — the robot's compute and I/O layer.

Systemcore is the main processor in the new FIRST control architecture. WPILib documents it as a controller built around a Raspberry Pi Compute Module 5 plus a reconfigurable I/O controller.

What it is responsible for

  • Running the robot program and WPILib runtime.
  • Providing network connectivity and USB/Ethernet interfaces.
  • Providing CAN and Smart I/O interfaces.
  • Providing an onboard IMU for orientation/robot-state applications.
  • Serving as the software boundary between the robot program and distributed devices.
Design principle: treat Systemcore as the compute layer. Keep motor-specific configuration and mechanism logic in well-defined subsystems rather than scattering device calls through the robot program.

2027 software changes to remember

  • WPILib 2027 reorganizes Java packages from edu.wpi.first to org.wpilib.
  • The 2027 stack changes gamepad APIs and several motor/controller method names.
  • NetworkTables 3 support is removed in favor of NetworkTables 4.
  • Systemcore has different hardware support than the roboRIO; do not blindly port old hardware code.
Do not copy old examples blindly. Check the 2027 WPILib docs and the Systemcore testing repository for the version you are actually running.
05 · Hardware

Motioncore — simplify the power and CAN layer.

FIRST describes Motioncore as a communication and power distribution device designed around point-to-point device connections instead of the daisy-chain wiring traditionally associated with CAN.

Device ports

20 × device connections

Each device port provides CAN + power for an A301 or compatible smart device. The architecture makes individual device wiring easier to isolate and replace.

Bridge

Systemcore connection

The bridge connection carries power and communications between Motioncore and Systemcore. This is the main boundary between the power/device layer and compute layer.

Sensing

Quadrature inputs

Motioncore includes three quadrature encoder ports, useful for odometry or other external sensing where appropriate.

Design itemDocumented architectureEngineering implication
Device ports20 individual device portsDebug one actuator/cable path at a time.
Communication1 Mbps CAN device connections; CAN FD upstreamSeparate device-level faults from controller/software faults.
Encoder ports3 quadrature inputsUseful for external odometry/sensing designs.
ProtectionMonitoring, thermal/overcurrent protection featuresUse fault telemetry as part of validation rather than ignoring warnings.
06 · Hardware

FIRST A301 — one actuator, multiple control concepts.

FIRST describes the A301 as a standardized smart brushless actuator for the new control system, combining motor operation with closed-loop positioning behavior and an integrated output absolute encoder.

Where it fits in Swechanum

  • One A301 provides wheel drive at a swerve corner.
  • A second A301 provides steering at that corner.
  • Four modules therefore create an eight-actuator swerve drivetrain.
  • The same actuator concept can be reused for mechanisms, allowing students to learn open-loop and closed-loop control on the same hardware.

Feedback-first workflow

  1. Read the encoder without commanding motion.
  2. Verify the signal is valid and stable.
  3. Run low-power throttle with the mechanism unloaded.
  4. Verify velocity reporting.
  5. Only then tune position/steering control.
Important: the exact firmware/API behavior is version-dependent during alpha/beta development. Use the A301 documentation bundled with the matching Systemcore testing release.
07 · Electrical + mechanical

Design for serviceability, not just assembly.

Swechanum exposed a practical lesson: a robot can be mechanically correct and still be frustrating to operate if the battery, switch, cables, and service points are buried.

Electrical bring-up checklist

  • Battery connector fully seated and strain-relieved.
  • Motioncore bridge connection fully latched.
  • Each A301 cable routed without sharp bends or pull on the connector.
  • Unused ports protected from accidental shorts/debris.
  • Device labels match the software constants.
  • Fault LEDs/status are checked before escalating to software.

Mechanical packaging checklist

  • Battery can be removed without dismantling unrelated mechanisms.
  • Main power switch is reachable without tools.
  • Motor cables cannot contact rotating drivetrain parts.
  • Steering module has full intended rotation clearance.
  • Encoder/sensor cables have enough service loop.
  • Fasteners and connectors can be inspected after repeated driving.
08 · Software

Set up the development environment before building features.

Use the official WPILib 2027 documentation and the Systemcore testing repository as the version authority. REV's documentation should be used for REVLib installation/configuration where the library applies to your device/version.

1

Install the matching WPILib release

Use the 2027 WPILib installer/release that matches the Systemcore image you are testing. Returning teams should import/update older projects rather than assuming a 2026 project is already compatible.

2

Create or update the robot project

Keep constants, hardware abstractions, subsystems, and teleop/test modes separated. This becomes critical when one A301 test evolves into four swerve modules.

3

Add the appropriate vendor library

Follow the REV installation instructions for the exact REVLib release you are using. Do not mix a prerelease A301 API with an unrelated stable REVLib version.

4

Deploy the smallest test program

Start with one device and telemetry. A small test gives you a clean answer to the question: “Is the hardware/API path working?”

09 · Software

First motor test: prove the device before proving the drivetrain.

The exact A301 constructor and method names can change with prerelease REVLib versions. The pattern below is intentionally minimal; use the matching A301 API in your installed library.

Java · illustrative structure — verify against matching A301 API
// 1. Construct the device using the port/device mapping for your build.
A301 motor = new A301(/* Motioncore port / device ID */);

// 2. Read telemetry before trusting a command.
var velocity = motor.getEncoderVelocity();

if (velocity.isValid()) {
    System.out.println("Velocity: " + velocity.get());
}

// 3. Start with low-power throttle.
motor.setThrottle(0.10);

// 4. Stop explicitly when the test ends.
motor.stop();
API note: do not paste this snippet into a project without checking the A301 class/method names exposed by your installed REVLib build. The project should compile against one documented version, not a mixture of examples from different alphas.
10 · Drivetrain

Swerve: translate one driver command into four module states.

A swerve drivetrain is not simply eight motors running at once. The software continuously transforms chassis motion into a target angle and speed for every module, then each module performs its local control.

Gamepadvx · vy · ω
→
Field / robot transformIMU heading when field-centric
→
Swerve kinematicsChassisSpeeds → module states
→
Module optimizationShortest steering path
→
A301 controlSteer + drive

Engineering sequence

  1. Test drive motor direction.
  2. Test steering direction.
  3. Calibrate absolute steering zero.
  4. Close the steering loop.
  5. Build one complete pod.
  6. Duplicate to four modules.
  7. Run kinematics with the robot lifted.
  8. Run low-speed floor tests.
  9. Add field-centric control and odometry.

Module optimization

If the requested steering angle is more than 90° away from the current heading, rotate the wheel state by 180° and invert wheel speed. The robot produces the same net velocity while avoiding an unnecessary long steering movement.

Why it matters: this is one of the clearest examples of why feedback, geometry, and control software have to be designed together.

11 · Vision

Limelight: turn camera measurements into robot information.

Limelight's current documentation covers zero-code vision pipelines, AprilTags, NetworkTables, HTTP/REST, WebSockets, and more. For a competition robot, vision should be treated as another sensor subsystem with explicit calibration, validation, and fallback behavior.

AprilTag workflow

  1. Mount the camera rigidly.
  2. Record camera-to-robot position and orientation.
  3. Connect the camera to the robot network.
  4. Open the Limelight web interface.
  5. Verify AprilTag detection before writing robot code.
  6. Configure the appropriate robot-pose/field setup.
  7. Publish or consume vision measurements through the documented interface.
  8. Compare vision pose to a known robot position.

Validation rules

  • Do not accept a pose merely because a tag is visible.
  • Reject measurements with implausible jumps or poor geometry.
  • Test at multiple distances and angles.
  • Measure latency before using vision for fast control loops.
  • Document the camera transform and mounting revision.
  • Keep a non-vision fallback for basic driving.
Official starting point: Limelight's documentation is the source of truth for current pipeline, AprilTag, pose-estimation, and NetworkTables configuration.
12 · Engineering process

Use the robot as an engineering experiment.

The strongest part of Swechanum is not the final drivetrain. It is the repeatable process used to turn unknown hardware into a system that can be explained, tested, and improved.

01 · Define the requirement

What must the robot demonstrate? Define measurable goals such as steering range, response, repeatability, telemetry, and driver control.

02 · Research the constraints

Read official hardware specifications, software requirements, API documentation, competition rules, and known issues before designing around assumptions.

03 · Build the system architecture

Map power, CAN, compute, sensors, actuators, software layers, and human controls before assigning device IDs or writing subsystem code.

04 · Prototype the smallest unit

For swerve, the smallest useful unit is a single pod. For the electronics, it is one Systemcore → Motioncore → A301 path.

05 · Instrument everything

Telemetry should expose command values, measured values, validity, faults, and important state transitions. Debugging is faster when the system explains itself.

06 · Integrate one layer at a time

Motor → encoder → steering control → pod → four pods → chassis kinematics → field-centric control → odometry → vision.

07 · Validate and document

Record what passed, what failed, what changed, and which software/firmware versions were involved. A result without a reproducible setup is not finished engineering.

13 · Testing

Test from the bottom of the stack upward.

Level 01

Electrical

Power, connectors, protection, LEDs, battery behavior, cable strain, and thermal conditions.

Level 02

Device

One A301: discovery, firmware, throttle, encoder, velocity, position, faults.

Level 03

Subsystem

One swerve pod: steering + drive, calibration, optimization, repeatability.

Level 04

System

Four modules, chassis motion, kinematics, field-centric control, odometry.

Level 05

Vision

AprilTag detection, camera transform, pose accuracy, latency, rejection logic.

Level 06

Validation

Repeatability, edge cases, driver usability, serviceability, and regression testing.

14 · Troubleshooting

Debug by isolating the layer that is actually failing.

Robot does not connect

  1. Check power and Systemcore boot state.
  2. Check network/Driver Station connection.
  3. Check that the software image and Driver Station are compatible.
  4. Read the Systemcore display/status before changing code.
  5. Only after connectivity is proven, investigate robot code.

A301 does not respond

  1. Check the physical cable and correct Motioncore port.
  2. Confirm the expected device mapping/ID.
  3. Check firmware/library compatibility.
  4. Run the smallest single-motor test.
  5. Inspect device faults/warnings.
  6. Swap one known-good cable/device path if available.

Encoder values look wrong

  1. Verify the signal is marked valid.
  2. Check whether the code expects rotations, degrees, radians, or a normalized 0–1 position.
  3. Power-cycle after firmware/code changes if the test procedure indicates stale state.
  4. Compare raw telemetry to a physical reference position.

Swerve module spins the long way

  1. Check current angle convention.
  2. Normalize the requested angle.
  3. Apply 180° state optimization when the error exceeds 90°.
  4. Invert drive speed when the wheel state is flipped.
  5. Verify the steering encoder zero is mechanically correct.
Project lesson: Swechanum's original development included firmware/API mismatches, inconsistent encoder behavior after code deployment, and packaging conflicts around the battery/switch. Those are documented here as project-specific lessons, not universal behavior of every production revision.
